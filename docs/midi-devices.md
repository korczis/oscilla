# MIDI devices: profiles derived from the maker's own files (V507)

OSCILLA knows a controller by a profile: its names, its SysEx identity numbers, its memories,
and for each physical control the message it sends in its factory setup. The profiles are
`src/data/midi-devices.json`; `src/js/midi/devices.js` reads them to recognise an input and to
name the control behind a message. They are never typed by hand (rule
`project.midi-profiles-derived`): `scripts/midi/derive-devices.mjs` derives them from the
maker's editor files on a machine where it is installed, and the procedure is
`.ai/repo/workflows/midi-device-import.md`.

## What is read, and what is not

| Source (installed, never committed) | What is taken | What is left |
|---|---|---|
| Editor device description (`Resources/<device>.json`) | the device's names, manufacturer, family and member numbers, the number of memories, the controls with their kind and bank | the image, the editor layout, the updater, every key, the parameter editor's field table |
| Editor factory template (`Templates/<device>/Factory/Default.*`) | per control item: mode (param 1), channel (2), number (3), when the mode sends a CC, a switched CC or a note | values, names and every other parameter |
| Plug-in generic MIDI map (`<plug-in>/resources/plugin.prefmidi.xml` with `Reference_ParamNames.xml`) | per controller number: which plug-ins read it and the role word of the parameter most of them give it | the parameter lists, presets, samples, graphics, code |
| The device itself (`scripts/midi/identity.swift`, `scripts/midi/listen.swift`) | the identity reply and the messages each port sends | nothing is sent but the Universal Identity Request |

The full decode of every file read goes to `.local/midi/` for a person to inspect; `.gitignore`
ignores it. Firmware files and libraries are neither opened nor decompiled.

## The structures

A profile (`schema: 1`):

```
{ id, name, names: [model names the ports carry],
  identity: { manufacturer: [3 bytes], family: [2 bytes], members: [[2 bytes] per model] },
  memories: <count; the names stay in the dump>, controls: [{ id, kind, bank, message, channel, number }],
  source: { description, descriptionSha256, template, templateSha256 } }
```

`message` is `cc`, `cc-switch` (a button sending a CC), `note`, `nrpn` or `program`; `channel`
is 1-16, or `user`, `part1`, `part2`, `both` where the device's own setting decides.

## The identity reply, measured

A Universal Identity Request (`F0 7E 7F 06 01 F7`) answered on 2026-11-15:

| Device | Reply | Manufacturer | Family | Member | Version (LSB first) |
|---|---|---|---|---|---|
| KeyLab mkII 61 | `F0 7E 7F 06 02 00 20 6B 02 00 05 64 54 01 03 01 F7` | `00 20 6B` | `02 00` | `05 64` | 1.3.1.84 |
| BeatStep Pro | `F0 7E 7F 06 02 00 20 6B 02 00 07 00 06 01 00 02 F7` | `00 20 6B` | `02 00` | `07 00` | 2.0.1.6 |

Both match their profiles' identity numbers; the BeatStep Pro's version is the one of the
firmware file the editor ships, which fixes the byte order.

## Port roles

The operating system names each port of a device (`KeyLab mkII 61 MIDI`, `KeyLab mkII 61 DAW`,
`Arturia BeatStep Pro Arturia BeatStepPro`, `… BeatStepPro OutEditor`). For a known device a name
that says DAW (MCU, HUI) is a DAW-control port, whose Note On messages are buttons and never
sound; a name that says editor is the maker's editor port; every other port plays. A port of an
unknown device always plays.
