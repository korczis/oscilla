# CI browsers run AudioContext at 44.1 kHz and a Mac at 48 kHz, so a frame window comes from the context rate (wait.cjs frames), never a literal

Observed as defect about tests/browser/lib/wait.cjs in episode s-20261017232612-d03c.

# Evidence

- `commit:535af3b347443dfa05c16cb5fb67128637e3db1f`
- `commit:95561eeda476dd6d6459d051d4f8edfe5c49a7c6`
- `test:tests/unit/browser-timing.test.mjs`

# Evidence

Headless Chromium, Firefox and WebKit on the ubuntu CI runners open an AudioContext at
44.1 kHz; on the Mac they open it at 48 kHz. A window written as a frame count is therefore
right at one rate only, and the failure it produces is deterministic and identical in all
three browsers on CI while absent locally, which reads as a platform rate and not as
flakiness. Seen on 2026-10-03: an after-abort check scanned a fixed 280 frames (the limiter's
6 ms look-ahead at 48 kHz); at 44.1 kHz that is 264 frames, so the window caught the next
sweep's fade-in. A 2 ms window is 88.2 frames at 44.1 kHz.

What holds now: a window is seconds at the context's own rate, `frames(seconds,
ctx.sampleRate)` or `anchor(ctx).frames(seconds)` from `tests/browser/lib/wait.cjs`, which
throws on an assumed rate. Reproduce a CI-only failure in the Playwright linux/amd64 container.
This complements `audio-measurement-pitfalls` (forcing a context's rate), which does not state
the runner rates.

- commit 14c7d5fc1337a9d2534c66f1f0c77ef78013fb52 (#29): the after-abort window became
  floor(0.006 * sampleRate) - 8 after it scanned 280 frames at 44.1 kHz
- commit 535af3b347443dfa05c16cb5fb67128637e3db1f (#37): the transport suite compared on the
  0.5 ms grid because 2 ms windows are 88.2 frames at the runners' 44.1 kHz
- commit 95561eeda476dd6d6459d051d4f8edfe5c49a7c6 (#166): `project.bounded-test-timing` and
  `wait.cjs` `frames` / `anchor`
- test `tests/unit/browser-timing.test.mjs`: a frame window from an integer literal and an
  assumed sample rate are findings; `frames` and `anchor` take the window from the context rate
