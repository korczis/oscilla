# Browser suites must not pick random ports: on 2026-10-18 a majordomus server held 9507 and failed the release gate; dist is served by tests/browser/lib/serve.cjs on an OS-assigned port

Observed as defect about tests/browser/lib/serve.cjs in episode s-20261017232612-d03c.

# Evidence

- `commit:6b79ae55c03b2d2d353bbc34981266cbb4382212`
- `commit:2e05b7fd076b4995abf5e375d72319fce8d073c0`
- `test:tests/unit/browser-static-server.test.mjs`
- `issue:186`

# Evidence

The seven suites that load `dist/` over http (app, navigation, v3-ui and four Studio suites)
each drew a random port from a fixed range and never checked it was free. On 2026-10-18
`v31-studio-workflows` drew 9507, which another session's majordomus server held, and the
release gate failed with "server did not start" although the page was fine. Each suite also
waited for its server with a fixed 80 x 100 ms loop.

What holds now: a suite serves dist through `serveDist` in `tests/browser/lib/serve.cjs`. The
OS assigns the port; a server that exits before answering is retried on another port;
readiness is a `until()` poll with a named wall-clock deadline, and only a response with the
served file's length counts, so another process answering on the port is not taken for ours.
On a machine several sessions share, any fixed or random port in a known range is a collision
waiting to happen.
