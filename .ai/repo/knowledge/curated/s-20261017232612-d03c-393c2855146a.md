# An older Majordomus cannot read a newer .ai layer (it refuses unknown policy keys), so the CI pin and the migrated layer land in one pull request

Observed as drift about .github/workflows/ci.yml in episode s-20261017232612-d03c.

# Evidence

- `file:.ai/repo/adrs/0056-majordomus-pin-moves-with-the-layer.md`
- `commit:0dc83746766ca107f1e12b09577164d3ae91e91e`
- `test:tests/unit/majordomus-pin.test.mjs`

# Evidence

Every released Majordomus refuses an unknown policy key, and a newer release can require a key
or vendor a rule whose validator only it ships. So the pinned CI version (`MJ_VERSION` and
`MJ_SHA256` of the `knowledge` job in `.github/workflows/ci.yml`) and the `.ai/` layer must
move together whenever no layer reaches 0 doctor failures under both versions: 0.29.0 needs
`session.retention_max_files` and two vendored rules (3 failures without them), and 0.20.0
rejects those keys as unknown (4 failures with them). Split into two pull requests, one of
them always fails CI's pinned doctor.

The procedure `scripts/majordomus-pin-check.mjs` prints says when the steps land as one pull
request, the digest taken from `https://majordomus.dev/releases/v<new>.json`, and the PR body
shows both versions' doctor output.
