# Tests

`npm run release-gate` runs, in order: `verify`, `test:release`. `verify` runs, in order:
`scripts/disk-preflight.mjs`, `npm test`, `version:check`, `build:check`, `verify-dist`,
`scripts/majordomus-pin-check.mjs`, `majordomus doctor`. `test:release` runs, in order: `test:engine`, `test:dsp`, `test:labs`,
`test:sequencer`, `test:measure`, `test:studio`, `test:browser`, `test:visual`. These sentences
are `package.json`'s scripts, held by `unit/docs-derived.test.mjs`; the suites each script runs
are in the table below. CI runs the same scripts as parallel jobs aggregated by the required
`gate` job, plus a `knowledge` job that runs a pinned `majordomus doctor`
(`.github/workflows/ci.yml`).
`OSC_BROWSERS=chromium,firefox` narrows the multi-browser suites. `test:live` (post-deploy, needs
the network) is not in release-gate: the Pages workflow (`.github/workflows/pages.yml`) runs it on
every deployment, one browser per job, after `verify-deploy` has proven the page is the committed
dist, and a failed check fails the workflow; it can also be run by hand against the public site.
`test:perf` (startup and large-library budgets, wall-clock medians measured on the development
machine) is not in release-gate either: `docs/v4/performance.md` records the decision.

Classes: **GATE** fails a release · **SUPPORTING** data or helpers a gate needs · **DIAGNOSTIC**
for people, never gating · **DELETED** removed, with its replacement.

## The browser harness

Every suite under `browser/` runs through `browser/lib/suite.cjs` (rule `project.suite-harness`):

- `OSC_BROWSERS` (or the suite's `--browsers` / `--browser` flag) and `--origins` / `OSC_ORIGINS`
  select what runs. An empty list, an unknown name or a repeated one exits 2; a variable that is
  set and empty is an empty list, not "everything".
- A selected browser that ran 0 checks fails the suite, whatever it printed. So does a leg
  run on another engine: launching an engine outside the selection is refused, and a selected
  browser whose own engine never started fails at exit.
- Outside CI a suite waits for the 1-minute load average to fall below `OSC_LOAD_MAX` (default
  2 x cores) for at most `OSC_LOAD_WAIT_MS` (default 600000) and then fails without running; it
  prints the load at start and at end. Under CI (`CI` or `GITHUB_ACTIONS`) there is no gate.
  `npm run release-gate` and `npm run release:prepare` run the suites locally, each behind its
  own gate: on a machine that stays busy they wait and then fail, by design. Run them when it
  is quiet, or state the limit you accept (`OSC_LOAD_MAX=64 npm run release:prepare`).
- `npm test` has no load gate. Its Studio performance budgets
  (`unit/v31-studio-performance.test.mjs`) are judged on the main thread's CPU time, which a
  busy machine does not stretch (plan E029): at load 87 on 18 cores the build's fastest repeat
  was 2378 ms of wall time and 307 ms of CPU time. The load makes the file take longer, within
  its wall-clock deadlines; it does not move the numbers judged.
- Before any of that, `npm run verify` (and so `npm run release-gate`, once) refuses to start
  below `OSC_DISK_MIN_MB` (default 2048) free on the checkout's file system or the temporary
  directory's (`scripts/disk-preflight.mjs`, exit 1), naming the disk: on a full disk the
  gate's failures name everything but the disk. The value must be a number of at least 256
  (exit 2 otherwise, `0.001` included); there is no off switch. A free space it cannot read is
  exit 3. Free space instead (the `node_modules` of landed worktrees first).
- `page.evaluate` (and the page's `evaluateHandle`, `$eval`, `$$eval`) answers within
  `OSC_EVALUATE_MS` (default 300000) of wall time or rejects with the function it was running.

Waits follow rule `project.bounded-test-timing`: a new wait is a condition poll through
`browser/lib/wait.cjs` with a wall-clock deadline that names the check, never a fixed sleep, in
the suite or in the page. The fixed sleeps written before the rule are recorded debt in
`browser/timing-baseline.json`, which may only shrink. A deliberate exception carries `// timing-allow: <reason>` (three words or more) on its
line or the line above. `node tests/browser/lib/timing-scan.cjs` prints what the scan finds
beyond the recorded debt; after removing a sleep, `--write-baseline` lowers the record, which
otherwise leaves room for a new one.

## Declared skips

A check a suite does not run is taken through `RUN.skip(leg, id, reason)`. Under CI a skip that
is not listed here with its reason fails the suite, so no check stops running there unnoticed.

| Skip | Reason |
| --- | --- |
| `dsp:offline-analyser-variant` | the offline variant of the analyser peak check needs `OfflineAudioContext.suspend(t)`, which a browser may lack or refuse; the live analyser checks of the same suite cover the peak in every browser |
| `qa-regressions:contrast` | the contrast check is defined for Chromium only (`browsers: ['chromium']`); the reason was not recorded when it was written, and Firefox and WebKit do not run it |
| `qa-regressions:contrast-axe` | the axe-core colour-contrast pass runs only when axe-core is installed (`npm i --no-save axe-core`); it is not a dependency, so CI computes the contrast ratios without it |
| `app:phone-bars-with-microphone` | WebKit has no fake capture device, so the phone-bar states are checked there without an open microphone stream; Chromium and Firefox check both |
| `midi:midi-measured-grant` | Playwright's `midi` and `midi-sysex` grants change the outcome in Chromium only: Firefox refuses the names ("Unknown permission") and WebKit accepts them but has no Web MIDI (ADR 0058), so the grant, its resolved access and its revocation are measured in Chromium |
| `midi:midi-measured-revoke` | revocation needs an access to withdraw. Taken where Chromium's granted request ends `failed` (a platform without a MIDI backend, possible on the CI runners, which ADR 0058 did not measure) or, off darwin only, is still `pending` at its 30 s deadline: that outcome is checked (the copy of the state it is in) and printed on a `RECORD` line ("pending at the 30000 ms deadline") instead. | `midi:midi-measured-stub-fidelity` | WebKit has no Web MIDI interfaces (`MIDIAccess`, `MIDIInputMap`, `MIDIInput`) to compare the stub's members with; Chromium and Firefox, which expose them, run the comparison |
